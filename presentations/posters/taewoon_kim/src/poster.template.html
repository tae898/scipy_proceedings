The problem

Scientific Python increasingly mixes three kinds of data access over the same data — records (SQL), relationships (graph), similarity over embeddings (vectors). Today that means three separate systems + custom ETL + hand-kept consistency.

↓
The idea · the contribution

One embedded engine, in-process, one pip install

Documents, a property graph, and HNSW vectors in one process, one file-backed database, one transaction — no server. Engine = ArcadeDB (Apache-2.0 Java, credited); our contribution is the Python binding: JPype in-process JVM + NumPy/pandas API + a bundled per-platform JRE → 20 wheels, no Java to install.

A Java engine sealed inside a Python wheel: one process hosts an in-process JVM (via JPype) running ArcadeDB over a local file-backed DB; documents/SQL, property graph (Cypher) and HNSW vectors reached through one handle. Wheel ≈75 MB, plain pip install.
★ The payoff — one workflow, three models

Hybrid retrieval: vector → SQL → graph, one transaction

Given a seed question, find semantically similar ones, keep the well-scored, return their best answers with each author's reputation. Identifiers flow directly between steps — no serialization, no ETL, no second system.

# 1) VECTOR — questions similar to a seed
cands = db.query("sql",
  "... expand(vectorNeighbors(?,?,?,?)) ...",
  "Question[embedding]", seed, 200, 100).to_list()

# 2) SQL — keep well-scored (ids from step 1)
filt = db.query("sql",
  f"... WHERE id IN {ids} AND score >= 1 ...").to_list()

# 3) GRAPH — MATCH to answers + reputation
hits = db.query("sql",
  f"... MATCH {{Question id IN {fids}}}
    -HAS_ANSWER->{{Answer}}-AUTHORED_BY->{{Userx}} ...").to_list()

…and where it isn't (we don't hide it)

Specialists win heavy analytics: DuckDB ≈9 ms vs ≈1,180 ms (tabular OLAP); LadybugDB ≈77 ms vs ≈844 ms (graph, a GAV narrows the gap). The standing cost is memory — a JVM baseline (≈930 MiB tabular) above the lean C peers; startup is sub-second, with an occasional GC tail. But these gaps are a moving target: ArcadeDB ships ~monthly and the binding packages each release, so Python benefits automatically.

Use it when

  • local, reproducible, in-process work
  • >1 model over the same data
  • RAG / KB prototypes, teaching
  • "one pip install" matters

Reach past it when

  • one model dominates at scale
  • warehouse columnar scans → DuckDB
  • high-QPS vector serving
  • hard real-time latency SLAs
